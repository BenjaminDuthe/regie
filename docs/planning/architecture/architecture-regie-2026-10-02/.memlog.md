- (direction) Benjamin demande des microservices pour le découpage en processus ; granularité à préciser
- (decision) Paradigme de découpage : cœur métier unique (web, MCP, API, file, règles, statuts) + microservices techniques sans règle métier (transcription, modèle de langage, voix, rendu, capture, publication), chacun dans son conteneur ; les services techniques ne connaissent ni statut ni utilisateur ; empêche la divergence de parité et la double propriété des statuts
- (decision) Machine : nœud Proxmox principal de Benjamin, avec carte Intel Arc 10 Go de VRAM partagée avec Tdarr ; transcription et modèle de langage sur la carte graphique pour la bêta
- (assumption) La carte Intel Arc partagée avec Tdarr suffit pour la bêta (modèle de transcription + modèle de langage quantifié < 10 Go) ; risque de contention avec Tdarr, à chronométrer pour NFR-2
- (decision) Liaison cœur ↔ services techniques : file PostgreSQL ; le cœur dépose des tâches typées, chaque service tire les tâches de son type et dépose son résultat ; les services ne touchent que les tables de la file, jamais les tables métier ; seul le cœur lit les résultats et change les statuts ; empêche deux propriétaires d'un statut
- (decision) Modèle de montage : JSON propre à regie, schéma zod exporté en JSON Schema, champ de version ; seule description d'une vidéo, partagée par relecture, MCP, API et rendu
- (decision) Moteur de rendu : ffmpeg + libass (sous-titres et textes à l'écran en ASS, mise en avant mot à mot) ; éléments graphiques fixes en images préparées ; le rendu Chromium image par image est écarté (NFR-2)
- (decision) Fichiers : volume partagé monté dans les conteneurs (pas de stockage objet) ; adresses signées expirantes (NFR-18) servies par le cœur ; cloisonnement des chemins à garantir par règle
- (decision) Capture : un conteneur jetable sans privilège par capture, réseau isolé vers un proxy filtrant (hôtes autorisés seulement, IP privées refusées, refus tracés), volume limité au dossier de sortie de la tâche, secrets limités aux identifiants de démo de l'application jouée ; seul le service capture accède au moteur de conteneurs (rootless)
- (decision) Envoi reprenable : protocole tus (@tus/server dans le cœur, client tus dans le navigateur), fichiers écrits dans le volume partagé
- (decision) Modèle de langage : service llama.cpp derrière une API compatible OpenAI, sorties contraintes par schéma JSON, modèle épinglé par version (FR-30) ; choix du modèle (licence Apache-2.0/MIT, tient dans 10 Go avec la transcription) reporté au banc de rushes français
- (decision) Îlots interactifs en Svelte dans Astro ; Astro + @astrojs/node en mode middleware sous Fastify [ADOPTED de l'ancienne architecture]
- (decision) Enregistreur de clics : navigateur distant dans le même conteneur isolé que la capture, écran relayé en direct dans la page (screencast CDP), clics et saisies relayés puis convertis en étapes ; aucune extension
- (decision) Aperçu des corrections : le lecteur du fil joue la version allégée en sautant les coupes et dessine sous-titres et textes depuis le montage JSON ; nouvelle version allégée rendue ensuite en tâche prioritaire ; rendu complet à l'export ou à la publication seulement
- (decision) Cloisonnement : double barrière, acteur obligatoire passé à chaque service + RLS PostgreSQL sur chaque table liée à un espace ou un utilisateur
- (decision) Secrets vers services techniques : la tâche ne porte qu'une référence ; le service échange auprès du cœur, sur réseau interne, un ticket lié à la tâche, à usage unique et expirant ; le secret n'existe qu'en mémoire ; la clé maîtresse ne sort jamais du cœur
- (decision) Langages : cœur et services capture, rendu, publication en TypeScript ; services IA (transcription, modèle de langage, voix) en Python ; conséquence : contrats (tâches, montage, erreurs) source unique en zod dans un paquet commun, exportés en JSON Schema, consommés par Python via modèles générés ; test de dérive bloquant ; la file est un protocole SQL documenté, pas une bibliothèque propre à un langage
- (decision) Sauvegarde : dump PostgreSQL cohérent chaque nuit + Proxmox Backup Server (VM et volume, incrémental, dédupliqué) + copie hors site ; restauration test mensuelle dans une VM jetable
- (decision) Courriel : SMTP vers un relais réglé par l'administrateur dans l'interface (identifiants au coffre) ; envoi par la file, échec tracé, sans bloquer
- (decision) Sessions en base : identifiant opaque en cookie HttpOnly SameSite=Lax Secure ; révocables (changement de mot de passe, blocage NFR-20, suppression de compte) ; remplace le cookie signé
- (assumption) Accès à l'Arc inconnu (Tdarr en LXC ou en VM avec passage PCI) ; cible : regie en LXC avec /dev/dri partagé ; vérification sur le PVE = première tâche d'installation ; repli : services IA sur CPU
- (decision) Reprises de l'ancienne architecture [ADOPTED] : zod aux bornes, scrypt pour les mots de passe, coffre AES-256-GCM avec clé maîtresse en environnement, routes publiques énumérées dans le code, migrations SQL numérotées appliquées au démarrage, planificateur à réveil calculé avec rattrapage borné à 2 h, journal applicatif JSON distinct du journal d'audit

- (decision) Les services lèvent ErreurMetier ; les façades traduisent. Signature AD-1 : (acteur, entrée) → résultat, lève ErreurMetier.
